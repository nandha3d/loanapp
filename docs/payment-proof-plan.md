# Payment Proof (Photo / QR) — Plan

**Goal:** every client→agent payment is proven, either by **photo + client approval** or by **client-generated QR that auto-approves on scan**. Agent toggles the mode per payment.

## Locked decisions
1. **Client surface:** existing **web borrower portal** (`/borrower/*`). Client logs in to approve photos + generate QR.
2. **Mode toggle:** **per-payment** — agent picks Photo or QR at collection time.
3. **Photo timing:** loan is **NOT** touched until the client approves. Agent "Paid" only files a pending request.
4. **QR:** client enters amount + generates a **single-use, day-expiring** signed token (QR encodes it + amount + instalment). Agent scans → backend validates → **verified** entry created automatically.

## Data model (new)

```prisma
model PaymentApproval {            // photo-proof pending requests
  id, tenantId, branchId?, loanId, instalmentId, customerId, agentId
  amount        Decimal
  paymentMode   String  @default("cash")
  proofType     String              // 'photo'
  photoPath     String?             // /api/files/... uploaded proof
  status        String  @default("pending")   // pending|approved|rejected|expired
  rejectedReason String?
  collectionEntryId String?         // set once approved
  createdAt, respondedAt?
  @@index([tenantId, status]) @@index([customerId, status])
}

model ClientPaymentToken {         // QR tokens generated by the client
  id, tenantId, customerId, loanId, instalmentId
  amount        Decimal
  token         String  @unique     // random; embedded in QR
  status        String  @default("active")  // active|used|expired
  collectionEntryId String?
  createdAt, expiresAt, usedAt?
  @@index([tenantId, status])
}
```

`CollectionEntry` keeps `verificationStatus` (`verified` for QR + approved-photo). No schema change to it required.

## Flows

### A. Photo proof (approval required)
1. Agent app: collect sheet → mode = **Photo** → snap photo (image_picker) + amount → **Paid**.
2. Upload photo → POST `/api/v1/collection/proof/photo {instalmentId, amount, paymentMode, photoUrl}`.
3. Backend creates `PaymentApproval(pending)`. **Loan untouched.** Notify client (SMS + portal badge): "Agent recorded ₹X — approve".
4. Client portal `/borrower/dashboard` → Pending Approvals → sees photo + amount → **Approve / Reject**.
5. Approve → backend records the **verified** CollectionEntry against the instalment (reuse the actual-mode collection write), links it, marks approval `approved`; notify agent + client. Reject → `rejected` + reason; nothing applied; notify agent.

### B. QR proof (auto-approve)
1. Client portal → enter amount + pick instalment (default: oldest unpaid / today) → **Generate QR** → POST `/api/v1/portal/qr` → `ClientPaymentToken(active, expiresAt = end of day)`. Portal renders QR encoding `loanpay:<token>`.
2. Agent app: mode = **QR** → scanner (mobile_scanner) → decodes token → POST `/api/v1/collection/proof/qr {token}`.
3. Backend validates token (active, not expired, tenant/route scope) → records **verified** CollectionEntry for the token's instalment+amount → marks token `used` + links entry. Notify client: "Payment confirmed".

## Endpoints
- `POST /api/v1/collection/proof/photo` (agent) — file pending photo approval.
- `POST /api/v1/collection/proof/qr` (agent) — scan token → verified entry.
- `GET  /api/v1/collection/approvals?status=` (agent) — track own requests (optional).
- Borrower portal (web, server actions or `/api/portal/*`):
  - generate QR token, list pending approvals, approve/reject.

## Shared write path
Approved-photo and QR both create the CollectionEntry via the **existing actual-mode write** (record on the specific instalment, no redistribution) with `verificationStatus: 'verified'`. Extract that into a reusable `recordVerifiedCollection(tx, {...})` helper so all three paths (cash, photo-approved, qr) stay consistent.

## Mobile (agent, Flutter)
- Collect sheet: segmented **Photo | QR** toggle.
- Photo: camera capture (have image_picker) + preview + amount → submit; show "awaiting client approval".
- QR: add `mobile_scanner` dep → scan screen → submit token → success.
- Optional "Pending Approvals" list (status of photo requests).

## Borrower portal (web)
- `/borrower/dashboard`: **Pending Approvals** card (photo + amount + Approve/Reject) and **Pay via QR** (amount + instalment → QR image, with countdown/expiry).
- Auth via existing `getBorrowerSession()`.

## Notifications
New `notify` events: `payment_pending_approval` (→client), `payment_approved`/`payment_rejected` (→agent), `payment_confirmed` (→client). Use SMS + `systemNotification` portal badge. (Client web-push optional later.)

## Phases
1. **Schema + migration** + `recordVerifiedCollection` helper.
2. **Agent endpoints** (`proof/photo`, `proof/qr`) + notify events.
3. **Borrower portal** (generate QR, list/approve/reject) + portal endpoints.
4. **Mobile UI** (mode toggle, photo capture, QR scanner).
5. Polish: approvals list, expiry sweeper, receipts.

## Open/none-blocking
- Token signing: random 32-byte token stored server-side (lookup) — no client-side secret needed.
- Expiry: tokens expire end-of-day; a lazy check on scan + optional cron sweep.
